# Overview

We will implement the initial version of the quantitative trading system in this project.

We'll use @notebooks/strategy_1.ipynb as our first implementation.

# Application Structure

Application consists of two parts (which are under @system/apps/):
- `trader`: This is the main application that will be responsible for trading. It will read required data from various sources, decide whether to buy/sell/hold based on the strategy, and execute the trades. It will also log the trades and their results for further analysis.
- `monitor`: This is the monitoring application that will be responsible for monitoring the performance of the trading system. It will read the logs generated by the trader application and provide insights into the performance of the trading system. It will also provide alerts in case of any issues or anomalies.

## Trader

The trader application will be the core of our quantitative trading system. It will be responsible for executing trades based on the implemented strategy.

For the implementation, there exists several core concepts in our mental model:

### DataFeed

The DataFeed interface will be responsible for providing the necessary data to the trader application. 
It will fetch data from various sources and make it available to the strategy.
For the efficiency, we'll store the fetched data in a local database (sqlite) for quick access, and won't do the fetch work if the data is already available in the database. 
The DataFeed will be responsible for managing the data feed, such as creating and updating the data feed tables in the database.

It extends `pd.DataFrame` and has the following additional properties and methods:
- `START_DATE`: If it's time-series data, this property will represent the start date of the data feed. It will be used to determine the range of data that needs to be fetched.
- `update()`: This method will be responsible for fetching the latest data from the data source and updating the internal state of the DataFeed.

### Strategy

The Strategy interface will be responsible for implementing the trading strategy. It will use the data provided by the DataFeed to make decisions about whether to buy, sell, or hold a particular asset.

Note that this must not touch real broker clients. It should only provide the decision to the trader application, which will be responsible for executing the trades.

### Trader

Trader is the main class that will be responsible for executing trades based on the implemented strategy. It will use the DataFeed to get the necessary data and the Strategy to make decisions about whether to buy, sell, or hold a particular asset. For broker client, we will use `tossinvest` as our broker client for the initial implementation. For the API documentation, please refer to https://developers.tossinvest.com/docs . Credentaials for the broker client are available in @.env .

## Monitor

The monitor application will be responsible for monitoring the performance of the trading system. It will read the logs generated by the trader application and provide insights into the performance of the trading system. 

Implemented with `streamlit`, it will provide:

- An overview tab that will show:
  - If the KRX market is open or closed.
  - The current balance of the trading account.
  - The current positions held by the trader application.
  - The performance metrics of the trading system, such as profit/loss, win rate, and other relevant information.
  - Latest trades executed by the trader application.
  - A chart showing the performance of the trading system over time.
- A data feed tab that will show:
  - The list of available data feeds.
  - The last update time of each data feed.
  - The ability to update the data feed by clicking a button.
  - The ability to delete the data feed by clicking a button.
- And each data feed page that will show:
  - The data feed name.
  - The last update time of the data feed.
  - The ability to update the data feed by clicking a button.
  - The ability to delete the data feed by clicking a button.
  - A table showing the data in the data feed.
- A trades tab that will show:
  - The table of trades executed by the trader application.
  - The details of each trade, such as the asset traded, the quantity, the price, and the result of the trade.
- A settings tab that will show:
  - The toggle to enable/disable the trader application.

Also, add Google login functionality, and restrict the access to the monitor application to only authorized users. This authorized users are given as a comma separated list of email addresses in the `AUTHORIZED_USERS` environment variable.

# Common Architecture

## Database

We'll use `sqlite` as our database for the initial implementation. It should consist of:

- `metadata.db`: This database will store metadata about the trading system, such as trade history, performance metrics, and other relevant information. It will be used by both the trader and monitor applications to store and retrieve data.
- `feed.db`: This database will store the data fetched from various sources by the DataFeed. It will be used by the trader application to access the necessary data for executing trades. It should have a table called `_metadata` that will store metadata about the data feed, such as data feed name, last update time, and other relevant information. The database consists of `_metadata` table and user defined data feed tables. The user defined data feed tables will be created by the DataFeed implementation based on the data source. It should be able to manage data feed tables, such as reading and deleting, in the monitor application.
